# Фронтенд фазы 2 — техническое устройство

Дата: 10.09.2026. Статус: согласовано.

Этот документ отвечает на вопрос **как**. На вопрос **что** отвечает
[docs/FRONTEND.md](../../FRONTEND.md) — там контракты ручек, описания
экранов и правила показа, и переписывать их сюда незачем. Здесь только
решения, которых в ТЗ нет или где ТЗ разошлось с действительностью.

---

## 1. Зачем это делается сейчас

Три Telegram-бота стоят с 08.09.2026: Telegram закрыл последний доступный
с российского VPS адрес. Шеф остался без рабочего инструмента совсем.
Бэкенд платформы готов и проверен, но пользоваться им можно только через
`curl` — то есть никак.

Фронтенд закрывает главный оставшийся пункт фазы 2. Всё остальное в этой
фазе без него бесполезно.

## 2. Расхождение ТЗ с действительностью: вход

Раздел 3 ТЗ велит фронтенду ходить за токеном прямо в Supabase:
`POST {SUPABASE_URL}/auth/v1/token`. В развёрнутом виде это невозможно по
трём независимым причинам:

1. `SUPABASE_URL=http://127.0.0.1:8000` — из браузера недостижим.
2. Наружу смотрит только nginx на 80 и 443, Supabase он не проксирует.
   Открыть его наружу запрещено правилом в `CLAUDE.md`: за шлюзом полный
   доступ к базе, а защита — одна пара логин/пароль.
3. Наш собственный CSP `default-src 'self'` запретил бы браузеру такой
   запрос, даже будь адрес доступен.

При этом в `infra/nginx/kitchen-platform.conf` **уже** объявлен блок
`location /api/auth/` с ограничением 10 запросов в минуту, проксирующий на
бэкенд, а в `.env.example` — переменная `SESSION_COOKIE_SECURE`. Правильный
ответ был заложен заранее; в ТЗ уехала другая редакция.

**Решение.** Вход идёт через свои ручки, бэкенд ходит в GoTrue со стороны
сервера, браузер получает httpOnly-куки и токена не видит вовсе.
`SUPABASE_ANON_KEY` перестаёт быть переменной сборки фронтенда.

Правку в ТЗ вношу отдельным пунктом: раздел 3 переписывается под эти
ручки, чтобы документ не остался с неработающей инструкцией.

## 3. Ручки входа

Новый модуль `backend/src/kitchen/web/auth_api.py`, префикс `/api/auth`.

### `POST /api/auth/login`

Тело: `{"email": "...", "password": "..."}`.

Бэкенд обращается к `{SUPABASE_URL}/auth/v1/token?grant_type=password` с
заголовком `apikey: {SUPABASE_ANON_KEY}` через `httpx` (уже в
зависимостях), таймаут 10 секунд.

- Успех: ставит две куки (см. ниже), отвечает **тем же телом, что
  `/api/me`** — почта, имя, роли. Так фронтенд после входа сразу знает,
  кого показывать в шапке, и не делает второй запрос.
- Неверная пара: `401` с текстом «Неверная почта или пароль». Разницу
  между «нет такого пользователя» и «пароль не тот» наружу не выносим —
  это подсказка тому, кто подбирает.
- Токен верный, а профиля в нашей таблице нет: `403` с текстом про
  администратора. Это уже делает `load_user`, поведение то же.
- GoTrue недоступен или ответил не пойми что: `502` с текстом «Служба
  входа не отвечает». Отличать это от неверного пароля обязательно —
  иначе шеф будет перебирать пароли при лежащем Supabase.

### `POST /api/auth/refresh`

Тела нет, refresh-токен приходит кукой. Обращается к
`grant_type=refresh_token`, переставляет **обе** куки: GoTrue вращает
refresh-токены при использовании, и сохранение старого означает, что
следующее продление откажет. Отвечает телом `/api/me`.

Если куки нет или GoTrue отверг — `401`.

### `POST /api/auth/logout`

Гасит обе куки (`Max-Age=0`). Отвечает `204`. Обращения к GoTrue не
делает: отзыв сессии на стороне Supabase здесь не нужен, а лишний сетевой
вызов на выходе — лишняя точка отказа.

### Куки

| Кука | Путь | Срок | Содержит |
|---|---|---|---|
| `kp_access` | `/api` | `expires_in` из ответа GoTrue (обычно час) | access-токен |
| `kp_refresh` | `/api/auth` | 30 суток | refresh-токен |

Флаги обеих: `HttpOnly`, `SameSite=Strict`, `Secure` — из
`settings.session_cookie_secure`, чтобы на `http://localhost:5173` в
разработке вход работал.

Пути разные и это осознанно: refresh-токен уходит на сервер только при
обращении к самим ручкам входа, а не в каждом запросе за списком блюд.
Статика кук не получает вовсе — она лежит вне `/api`.

CSRF отдельной защиты не требует: `SameSite=Strict` плюс то, что весь
читающий API на `GET` и того же происхождения. Когда в фазе 3 появится
запись, к этому надо вернуться — записывающие ручки на `POST` меняют
расклад.

### Правка в `auth.py`

`current_user` берёт токен из заголовка `Authorization` **или** из куки
`kp_access`. Заголовок остаётся рабочим: им пользуются `curl`,
`scripts/grant_access.py` и существующие тесты, и ломать работающее ради
единообразия незачем.

Порядок: сначала заголовок, потом кука. Явно переданный токен должен
побеждать — иначе отладка через `curl` с чужой кукой в браузере даёт
необъяснимый результат.

## 4. Раскладка фронтенда

Отдельный каталог `frontend/` рядом с `backend/`: своя сборка, свой
линтер, свой прогон тестов.

```
frontend/
├─ package.json, vite.config.ts, tsconfig.json, index.html
├─ src/
│  ├─ main.tsx, App.tsx
│  ├─ api/
│  │   client.ts    обёртка над fetch: 401 → refresh → повтор; 403 наверх
│  │   types.ts     контракты ручек, один в один с ТЗ
│  │   queries.ts   хуки TanStack Query
│  ├─ auth/
│  │   session.tsx  контекст вошедшего
│  │   LoginPage.tsx
│  │   RequireAuth.tsx
│  ├─ shell/
│  │   Layout.tsx   шапка + меню + область содержимого
│  │   Nav.tsx      все десять разделов карты 1.1, включая заглушки
│  ├─ ui/
│  │   DataTable.tsx  таблица/список, одна реализация на обе ширины
│  │   Num.tsx        число, прочерк, единица, табличные цифры
│  │   NameDiff.tsx   посимвольная подсветка различий
│  │   Badge.tsx, Icons.tsx
│  ├─ pages/
│  │   Ingredients.tsx, Dishes.tsx, DishDetail.tsx,
│  │   Reconciliation.tsx, Stub.tsx
│  └─ styles/
│      tokens.css   цвета, отступы, типографика
│      base.css
└─ tests/
```

**Стек.** React 18 + TypeScript + Vite. TanStack Query для серверного
состояния. Своё CSS без фреймворка — как требует раздел 2 ТЗ. Глобального
стейт-менеджера нет: состояние либо серверное, либо в адресе.

**Поиск и фильтр живут в query-параметрах адреса.** Ссылка на «блюда со
статусом активное, поиск „соус“» должна открываться тем же экраном:
шеф такие ссылки шлёт в переписке, и экран, теряющий фильтр при
перезагрузке, заставляет набирать всё заново.

**Шрифт кладём в сборку** пакетом `@fontsource/ibm-plex-sans` (и `-mono`
для чисел), а не тянем с `fonts.googleapis.com`, как это делает макет. CSP
`default-src 'self'` внешние источники запрещает, и на кухне Wi-Fi бывает
никаким — приложение не должно зависеть от Google, чтобы отрисовать цифры.

**Палитра — из макета** `docs/design/Kitchen App.dc.html`: тёплый серый
фон `#f2f2ef`, текст `#1a1b1d`, приглушённый `#6b6e73`, границы `#e2e2de`,
акцент `#2f5ecb`, внимание `#9a6400`, ошибка `#b3261e`. Один акцент и два
семантических, как требует раздел 7 ТЗ.

## 5. Обращение к API

`client.ts` — тонкая обёртка над `fetch` с `credentials: 'include'`.

Обработка кодов, и она разная не случайно:

- **401** — один раз дёрнуть `POST /api/auth/refresh` и повторить исходный
  запрос. Если refresh тоже 401 — сбросить сессию и показать форму входа.
  Повтор ровно один: цикл «401 → refresh → 401 → refresh» при протухшем
  refresh-токене крутился бы вечно.
- **403** — наверх как есть. Экран показывает сообщение и **не**
  отправляет на форму входа: человек уже представился, и повторный вход
  вернёт ровно то же самое.
- **5xx и обрыв сети** — сообщение «не удалось получить данные» с кнопкой
  «повторить». Молчаливо пустой экран запрещён: пустой справочник и
  недоступный справочник для шефа выглядят одинаково, а значат разное.

Параллельные 401 схлопываются в один вызов refresh: три запроса при
открытии экрана не должны давать три продления, из которых два отвергнутся
вращением токена.

## 6. Таблицы на обеих ширинах

`<DataTable>` принимает описание колонок:

```ts
type Column<T> = {
  key: string
  title: string
  align?: 'left' | 'right'
  priority: 'always' | 'wide'   // always — видно и на телефоне
  render: (row: T) => ReactNode
}
```

Шире 1080 px — настоящая `<table>` с плотными строками (25–30 на экран без
прокрутки). Уже — список, где видны только `always`-колонки, остальное
раскрывается по тапу.

**Одна компонента, а не два дерева разметки.** Два разъедутся на первой же
правке, и узкий вариант тихо отстанет от широкого — а он основной: боты
были стопроцентно телефонными.

Что остаётся на узком:

| Экран | Видно всегда | По тапу |
|---|---|---|
| Справочник | наименование, цена с единицей, отметка карточки | категория, вес штуки, статус |
| Блюда | название, UC ₽, маржа % | id, категория, цена меню, UC %, выход, замечания |

## 7. Правила показа — в компонентах, не в разметке экранов

Каждое правило раздела 6 ТЗ стоит за конкретным неверным решением, и
каждое закрепляется в одном месте, а не переписывается на каждом экране.

- `<Num value unit>` — `null` даёт приглушённый прочерк, визуально не
  похожий на ноль. Запятая как разделитель, `font-variant-numeric:
  tabular-nums`, выравнивание вправо, единица (`₽`, `г`, `%`, `шт`) явно.
- Строка, где `uc_rub > price_menu`, — красная, с подписью **«проверьте
  единицы измерения»**, а не «убыток». Так почти всегда и есть: перепутана
  единица или цена за упаковку записана как цена за килограмм.
- `warning_texts` выводятся списком целиком. Свернуть их в «есть 3
  замечания» значит отдать шефу число без основания.
- `kbju_coverage < 0.5` — пометка, что цифрам КБЖУ доверять нельзя.
- Архивные позиции **не прячутся**, а помечаются: они стоят в составе
  живых блюд, и без них не разобрать, почему у блюда такая себестоимость.
- `short_name` пустой — показываем `name`.
- Упаковка в составе блюда — отдельной группой в конце, брутто у неё нет.

## 8. Экран сверки

Главный экран фазы. Сверху сводка: всего, склеено, осталось. Дальше три
группы по `link_status`, и они требуют **разных** действий: выбрать из
вариантов (`ambiguous`), подтвердить или отвергнуть (`candidate`), завести
или отложить (`orphan`).

**Автоподстановки нет.** Ни кнопки «связать всё автоматически», ни
предвыбранного варианта. Один из кандидатов — «огурцы маринованные **не**
резаные» против «Огурцы маринованные резанные», похожесть 95%, смысл
противоположный. Подсвеченное как очевидное совпадение человек примет не
глядя, и себестоимость посчитается по чужой цене, выглядя при этом
совершенно правдоподобно.

`<NameDiff>` подсвечивает различие имён посимвольно: именно оно и есть
предмет решения.

Варианты `ambiguous` различаются **не именем** — они всегда полные тёзки.
Рядом с каждым показывается id, цена и единица, подтянутые из
`/api/ingredients` одним запросом на экран: «Сахар · 12 · 100 ₽/кг»
против «Сахар · 123 · 0 ₽/шт». Выбирают по ним.

**Кнопки действий на экране есть, но не работают** — ручек записи ещё нет,
и выдумывать их нельзя. Нажатие показывает, что действие появится в
следующей фазе.

## 9. Раздача и сборка

`infra/nginx/Dockerfile`, две ступени:

1. `node:22-alpine` — `npm ci`, `npm run build` в `frontend/`.
2. `nginx:1.27-alpine` — готовый `dist` копируется в
   `/usr/share/nginx/html`.

Node на сервере не нужен. `scripts/deploy.sh` не меняется — он уже делает
`up -d --build`, и сборка привязана к коммиту.

В `infra/docker-compose.yml` сервис `nginx` переходит с `image:` на
`build:` с контекстом в корне репозитория (нужны и `frontend/`, и
`infra/nginx/`).

В конфиге nginx:

- `location /` — `try_files $uri /index.html` вместо проксирования на API.
- `location /api/` — проксирование на `api:8080`.
- Хешированные ассеты — `Cache-Control: public, max-age=31536000,
  immutable`; `index.html` — `no-cache`. Иначе после выкладки шеф неделю
  смотрит старую версию и не понимает, почему ничего не изменилось.
- `/healthz` остаётся `404` наружу.
- Существующие `location /api/auth/` и `/api/chat/` с ограничением частоты
  сохраняются как есть.

CSP не меняется: `default-src 'self'` работает как есть — внешних
скриптов, стилей и шрифтов у нас нет.

## 10. Проверки

**Фронтенд:** Vitest + Testing Library + MSW. Моки повторяют ответы ручек
дословно — те, что выписаны в ТЗ, они настоящие.

По TDD в первую очередь закрываются правила раздела 6, потому что каждое
стоит за конкретным неверным решением:

1. `null` в цене меню даёт прочерк, и он отличим от нуля.
2. Блюдо с `uc_rub > price_menu` помечено красным, подпись — про единицы
   измерения, слова «убыток» в ней нет.
3. `warning_texts` показаны целиком, а не числом.
4. На сверке нет предвыбранного варианта и нет кнопки «связать всё».
5. `DataTable` на 360 px показывает только `always`-колонки и не даёт
   горизонтальной прокрутки.
6. 401 приводит к одному вызову refresh и повтору; второй 401 — к форме
   входа. 403 форму входа **не** показывает.

**Бэкенд:** обычный pytest с подменённым GoTrue (`httpx.MockTransport`).
Проверяется: успешный вход ставит обе куки с нужными флагами; неверная
пара даёт 401 и кук не ставит; недоступный GoTrue даёт 502, а не 401;
`refresh` переставляет обе куки; `current_user` принимает токен и из
заголовка, и из куки, и заголовок побеждает.

**CI:** новая задача `frontend` — `tsc --noEmit`, eslint, `vitest run`,
`vite build`. Полторы минуты, бюджет пяти минут держится. В `Makefile`
цели `front-lint`, `front-test`, `front-build`; `make check` их включает.

## 11. Чего в этой работе нет

- Тёмной темы — раздел 7 ТЗ, она не нужна.
- Ручек записи — фаза 3, и правило «пока живы боты, не пишем» никуда не
  делось.
- Подбора кандидатов для `candidate` — бэкенд отдаёт пустой массив, место
  под `score` рисуется заглушкой.
- Подробной вёрстки шести разделов-заглушек: пункт меню и страница
  «раздел появится позже».
- Регистрации, восстановления пароля, смены пароля — доступ заводит
  администратор через `scripts/grant_access.py`.

## 12. Известное ограничение приёмки

`art.karppacho.ru` не резолвится: A-записи на 153.80.247.91 пока нет.
Проверка на сервере до её появления возможна только по IP или изнутри,
и с самоподписанным сертификатом. Заявить «работает у шефа» до появления
записи нельзя — это надо помнить, объявляя работу законченной.
