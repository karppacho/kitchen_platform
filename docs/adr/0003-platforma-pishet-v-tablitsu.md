# 3. Платформа пишет в Google-таблицу: первая ступень — новая строка карточки

**Дата:** 2026-09-30
**Статус:** предложено

## Контекст

По ADR-0001, пока живы Telegram-боты, синхронизация идёт только в одну
сторону — лист → БД, и платформа в общие листы не пишет. В коде это держат
правила владения колонками (`kitchen/sync/ownership.py`): человеческие
колонки не пишутся никогда, общие — те, куда писали боты, — пока поднят флаг
`BOTS_ALIVE`.

Боты стоят с 08.09.2026 (Telegram закрыт с сервера), 09.09 сняты с
автозапуска, 23.09 решено, что они не вернутся. Шеф просит вернуть поток,
которым повара заводили карточки ингредиентов по фото этикетки. Бот
заканчивал его новой строкой в «Лист1» книги карточек — значит, это первая
функция платформы, которая пишет в таблицу.

Снять один флаг мало. Он открыл бы весь общий справочник кухни — ING,
Упаковку, Блюда, ТТК, — а пути записи у этой книги нет: ни сверки ячейки
перед записью, ни журнала правок, ни разбора конфликта с правкой шефа.

## Решение

Первая ступень записи — одна операция: **добавить новую строку карточки в
«Лист1» книги карточек.**

1. `BOTS_ALIVE = False` плюс второй замок — `WRITE_OPEN =
   frozenset({"ingredient_cards"})`, книги, у которых есть свой путь записи.
   Общую колонку можно писать, только когда сошлись оба условия. Книга
   кухни закрыта целиком, пока у неё не появится свой писатель.
   Человеческие колонки закрыты всегда, в любой книге.
2. Пишутся только колонки A–P и S–V. Q (декларация) и R (халяль-сертификат)
   заполняют люди — их не пишем никогда, даже пустым значением.
3. Только добавление: писатель пишет в строку, которая при чтении пуста во
   всю ширину, и никогда не выбирает строку с данными. Свободная строка
   (дальше — N) — первая после последней непустой ключевой колонки B,
   пустая во всю ширину (A–V и дальше). `append_row` и `values.append` не
   используются: они уводят запись вниз листа (разбор 04.08.2026). Что
   бывает, если шеф в это же время сдвинет строки, — в разделе об окне
   гонки ниже.
4. Перед записью — проверка двустрочной шапки той же функцией, что у
   импорта. Колонки съехали — отказ, ни одной записанной ячейки.
5. Запись — один запрос `values.batchUpdate` с `RAW` и двумя диапазонами,
   A–P и S–V. `RAW` кладёт текст как есть: строка с этикетки, начинающаяся
   с «=», остаётся текстом, а не становится формулой.
6. После записи — даже если запрос записи упал — строки N−1 и N
   перечитываются. Лист читается в двух видах, и у каждого своя роль:
   - **FORMATTED** (как видит шеф) — раскладка, снимки и хеш. Снимок «до»
     и сверка строки N−1 берутся в одном виде; хеш записанной строки —
     `row_hash` строки N целиком, A–V вместе с Q и R, ровно как её хеширует
     импорт: по нему перенос в базу узнаёт свою строку.
   - **UNFORMATTED** (числа числами) — значения строки N: отправленное
     сравнивается с перечитанным точно — текст как есть, без обрезки
     пробелов, число по значению (`Decimal(repr(x))`). Числа H–K уходят
     числами JSON, не текстом «12,5»: текст сломал бы шефу сортировку и
     формулы.

   **Раскладка подтверждена**, только если строка N−1 — та же, что при
   чтении листа, а в N лежит наша ссылка на фото этикетки (P). Ссылка
   уникальна для черновика, а фото этикетки обязательно у каждой карточки —
   по ней писатель опознаёт свою строку. Строку N−1 сверяют по B и P —
   имени и ссылке: шеф, дописавший в ту же секунду Q или R свежей карточке
   выше, подтверждение не ломает. Строку без имени — вторую строку шапки
   (у первой карточки N = 3) или чужую строку, которую писатель пропустил, —
   сверяют целиком: по пустым B и P сдвиг не виден.
   - Раскладка подтверждена и все 20 ячеек сошлись — запись состоялась
     (`verified`).
   - Раскладка подтверждена, но часть ячеек чужая — очищаются только ячейки,
     где лежит наше значение (очистка, а не удаление строки), — запись
     несостоявшаяся (`rolled_back`), черновик повара остаётся.
   - Запрос записи упал, строка N пуста, как при чтении, строка N−1 на
     месте — запись не легла (`failed`), чистить нечего.
   - Раскладка не подтверждена — не очищается ничего: в N может лежать
     чужая карточка. В журнале — `failed`, снимок строк N−1 и N, весь
     прочитанный лист и перечитанное. В лог — ERROR с номером строки и
     номером записи журнала. Повару: «Таблицу меняли в ту же секунду,
     запись не подтверждена. Покажите шефу строку N (запись журнала №J).
     Черновик сохранён.»
   - Чужую строку автоматически не чиним: на первой ступени — только разбор
     по журналу. Экрана журнала пока нет — разбор по базе и логу; экран —
     пункт ROADMAP (задача 12).
7. Писатели идут по одному — на своей блокировке в базе (не импортной:
   перенос листов в базу запись не ждёт). Ждать другого писателя дольше
   30 с — «Таблица занята». Каждая запись — в журнале `sheet_writes`:
   снимок «до» — строки N−1 и N целиком, вместе с Q и R, — значения,
   автор, ключ запроса. Запись `pending` ложится в журнал своим коммитом до
   записи в лист: упади процесс посреди записи — след останется.

   Повтор отправки второй строки не даёт — по двум признакам:
   - **ключ запроса** (на черновик — один). Открытая запись журнала с тем же
     ключом: состоявшаяся — ответ без единого запроса к Google;
     незавершённая (исход неизвестен: таймаут, и перечитать не удалось) —
     её строка перечитывается и решается тем же правилом, что после
     записи. Неясный исход решается перечитыванием, а не повтором записи;
   - **своя ссылка в P.** Точный дубль имени, у которого в P ссылка
     этикетки этого черновика, — наша прежняя попытка: например, раскладку
     не подтвердили, а строка всё же легла. Повтор отвечает этой строкой,
     ноль записей, в журнале — `verified` с пометкой «найдена прежняя
     попытка». Дубль имени с чужой ссылкой — отказ «уже есть в таблице —
     строка N».
8. В базу карточка попадает обычным переносом книги карточек, а не прямой
   вставкой: лист остаётся источником истины.

## Окно гонки с ручной правкой шефа

У `values.batchUpdate` нет условия «записать, только если ячейка не
менялась», а наша блокировка писателей шефа не касается. Окон три: между
чтением листа (выбор строки N) и записью — около секунды, между записью и
перечитыванием — доли секунды, и, если наши ячейки пришлось очищать, —
между перечитыванием и очисткой. В эти окна шеф может сделать то, что
касается нас: вписать что-то в строку N или в строку над ней, сдвинуть
строки — вставить или удалить строку выше N, отсортировать лист.

**Правка ячеек строки N.**

- *До нашей записи.* Его значения в A–P и S–V строки N перезаписываются
  нашими. Раскладка подтверждена (N−1 на месте, в P наша ссылка), и запись
  считается состоявшейся — эту потерю писатель не видит. Его Q и R
  остаются: мы их не пишем. Снимок «до» сделан при чтении и его значений не
  содержит; вернуть их можно из истории версий Google-таблицы, время и
  номер строки — в журнале.
- *После записи, до сверки.* Раскладка подтверждена, но ячейка чужая:
  писатель очищает только свои ячейки, его значение остаётся. Запись
  несостоявшаяся (`rolled_back`), повар отправляет карточку ещё раз.

**Правка строки N−1.** Шеф дописывает Q или R свежей карточке над нашей —
частый случай. Строку N−1 сверяют по B и P, поэтому такая правка — не
сдвиг: запись подтверждается как обычно.

**Сдвиг строк.**

- *До нашей записи.* Шеф вставил строку выше — последняя карточка съехала
  из N−1 в N. Мы перезаписываем её A–P и S–V, а её Q и R «прилипают» к нашей
  карточке. Одна сверка строки N этого не заметила бы — в N лежит наше, —
  и карточка пропала бы молча. Поэтому сверяется ещё и N−1: там теперь
  другое, раскладка не подтверждена, не очищается ничего, журнал —
  `failed`. Затёртая карточка целиком, с Q и R, лежит в снимке «до» —
  по нему её восстанавливают вручную.
- *Сдвиг на k ≥ 2 строк до записи.* Затёрта карточка из строки N−k —
  её нет в снимке строк N−1 и N. Сдвиг ловится так же: в N−1 теперь
  вставленная пустая строка или другая карточка. Поэтому при неподтверждённой
  раскладке в журнал ложится ещё и **весь прочитанный лист** (FORMATTED):
  затёртая карточка есть в нём, где бы она ни стояла.
- *Удаление строки выше до записи.* Наша строка ложится с пустой строкой над
  собой; N−1 не совпадает, запись — `failed`. Строка при этом легла, и
  повторная отправка находит её по своей ссылке в P: ответ этой строкой,
  второй строки нет.
- *После записи, до сверки.* Шеф вставил строку выше — наша строка уехала
  в N+1, а в N оказалась существующая карточка. Откат «очистить ячейки,
  равные нашим» стёр бы у неё совпавшие ячейки: категорию, поставщика,
  «Да». Раскладка не подтверждена (N−1 другая, в P не наша ссылка) — не
  очищается ничего; наша строка остаётся в N+1, журнал — `failed`.
- *Окно очистки.* Очистка своих ячеек идёт только при подтверждённой
  раскладке, но между перечитыванием и очисткой шеф тоже может сдвинуть
  строки — тогда очищены ячейки уже не нашей строки. Это два действия шефа
  за одну секунду. После очистки строка N−1 перечитывается ещё раз (B и P):
  не та — `failed` с полным снимком листа и ERROR в лог; упала сама
  очистка — так же.
- Сдвиг не виден, только если в N−1 после него оказалась строка с теми же
  B и P, что в снимке, то есть две карточки с одним именем и одной ссылкой
  подряд. Тогда затёртая строка — копия соседней.

Почему окна принимаем:

- Окна — около секунды, и строка N при чтении пуста во всю ширину: шеф
  должен в ту же секунду начать именно эту строку или сдвинуть строки.
- Сдвиг писатель замечает и ничего не чистит вслепую; затёртая строка
  восстанавливается из снимка в журнале. Незамеченной остаётся только
  правка шефа в N перед самой записью — несколько ячеек новой строки,
  которые есть в истории версий.
- Если шеф в окне сотрёт P у свежей нашей строки, повторная отправка её
  не узнает и упрётся в дубль по имени — разбор по журналу.
- Закрыть окна нечем, кроме защиты диапазонов листа, а она мешала бы шефу
  работать в собственной таблице.

## Последствия

- Для книги кухни ADR-0001 остаётся в силе: там только чтение. Для книги
  карточек синхронизация перестаёт быть строго односторонней — появляется
  одна операция записи.
- Следующая книга (справочник, блюда, расчётка) открывается отдельным
  решением вместе со своим писателем: сверка ячейки с прочитанным перед
  записью, журнал правок, разбор конфликтов. До него её нет в `WRITE_OPEN`.
- Правка существующих строк карточек — не эта ступень. Затёртую при
  сдвиге строку чинит человек по журналу; автоматической починки нет.
- `BOTS_ALIVE = True` остаётся аварийным рычагом: если какой-то бот ожил,
  общие колонки, в том числе карточки, снова закрыты целиком.
- Статус «принято» — после живой проверки записи на рабочей таблице.
