# 2. Supabase — хранилище, Studio и аутентификация, но не бэкенд

**Дата:** 2026-09-08
**Статус:** принято

## Контекст

Нужна БД под платформу. Выбран self-hosted Supabase на том же VPS: он даёт
Postgres плюс Studio — веб-интерфейс, чтобы «просто открыть и посмотреть
данные». Сегодня эту роль выполняет Google-таблица, и когда истина переедет
в БД, эквивалент необходим; своя админка стоила бы недель.

Supabase при этом предлагает и готовый бэкенд: PostgREST генерирует API
прямо из схемы, RLS раздаёт права на уровне строк.

## Решение

Берём Postgres, Studio и GoTrue (аутентификация). **PostgREST и RLS не
используем** — API пишем на FastAPI. Схема живёт под Alembic, а не под
миграциями Supabase CLI.

## Почему

Два слоя доступа к данным с разными правилами — это не «запасной вариант»,
а источник вопроса «где чинить», на который через полгода никто не ответит.
Бизнес-логика здесь нетривиальная (владение колонками, инварианты расчёта),
и она не выражается политиками RLS.

Отдельная выгода — обратимость. Под нами остаётся обычный Postgres:
если Supabase окажется лишним слоем, уход стоит `pg_dump` и смены строки
подключения, а не переписывания приложения.

## Последствия

- Из одиннадцати сервисов поднимаем шесть: `db`, `auth`, `api-gw`,
  `studio`, `meta`, `supavisor`. Шлюз — Envoy, а не Kong: upstream
  перестроился, и рецепты с сервисом `kong` больше не подходят.
  Замерено на сервере 09.09.2026 — стек занимает 581 МБ.
- Подключение приложения — через пулер (6543, transaction mode), Alembic —
  через 5432 (session mode) либо напрямую к `db:5432` внутри сети docker.
  Имя пользователя у пулера обязано нести идентификатор арендатора:
  `postgres.<tenant>`.
- Вход по паролю: self-hosted GoTrue не имеет своего почтовика, а письма с
  российского VPS без SPF/DKIM уходят в спам. Магик-ссылки — когда появится
  SMTP-релей.
- Эксплуатация наша: бэкапы `pg_dump` по крону с проверенным
  восстановлением, пиннинг образов по версиям, Studio только через
  SSH-туннель.
