Миграция выполняется на боевой базе один раз и без второго шанса. Проверяй
жёстко.

Отвечай по-русски. Пиши только найденное.

## Правила

**Обратимость**

1. У каждой ревизии есть рабочий `downgrade`. `pass` в `downgrade` допустим
   только там, где откат физически невозможен, и с комментарием, почему.
2. `upgrade` → `downgrade` → `upgrade` обязан проходить на непустой базе.
   Если ревизия этого не переживает — она не готова.
3. Ревизия не удаляет данные без явного намерения, записанного в докстринге.
   `drop_column`, `drop_table`, `DELETE`, сужение типа — каждое требует
   отдельной строки «почему это безопасно и что будет с существующими
   значениями».

**Совместимость с работающим кодом**

4. **Сначала совместимая схема, потом код.** Колонка добавляется nullable →
   деплой кода → заполнение → только потом `NOT NULL`. Между применением
   миграции и рестартом процесса есть окно, в котором старый код работает с
   новой схемой; он не должен падать.
5. `ALTER COLUMN ... SET NOT NULL` на непустой таблице без предварительного
   заполнения — отказ.
6. Переименование колонки в одной ревизии ломает работающий процесс.
   Правильно: добавить новую, синхронизировать, переключить код, удалить
   старую — четыре шага, не один.

**Производительность и блокировки**

7. `CREATE INDEX` на живой таблице блокирует запись. Нужен
   `CREATE INDEX CONCURRENTLY`, а он **не работает внутри транзакции** —
   ревизии нужен `autocommit_block()`.
8. У каждого внешнего ключа должен быть индекс. Postgres его не создаёт сам,
   и это регулярно всплывает как «непонятно почему медленно».
9. `ADD COLUMN` с `DEFAULT` на большой таблице в старых версиях переписывал
   её целиком; проверь, что версия сервера это делает дёшево.

**Дисциплина**

10. Одна ревизия — одно осмысленное изменение. Ревизия, которая правит схему
    и заодно переливает данные, откатывается плохо.
11. `down_revision` указывает на реальную голову. Две головы в графе — дефект
    слияния, а не «потом разберёмся».
12. Ревизия не импортирует модели приложения. Модели меняются, миграция
    описывает состояние на свой момент и обязана остаться воспроизводимой.

## Что делать

1. Найди новые ревизии: `git diff --name-only origin/main...HEAD -- backend/alembic/versions`.
2. Прочитай каждую целиком, включая докстринг.
3. Проверь связность графа: `cd backend && uv run alembic heads` — голова
   должна быть одна.
4. Для каждой проверь правила выше и ответь: **что произойдёт, если эта
   миграция применится, а новый код не запустится?**

## Формат ответа

Файл, номер ревизии, нарушенное правило, последствие на боевой базе,
минимальная правка. Сначала необратимое.

Нет замечаний — скажи одной строкой.
